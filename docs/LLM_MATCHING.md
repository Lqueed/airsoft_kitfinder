# Умный матчинг через LLM — статус и как это работает

Рабочая дока по этапу [M10](ROADMAP.md). Фиксирует, что уже сделано, как запускать
и что осталось — чтобы не терять контекст между сессиями.

## Зачем

Токен-`match_key` (`services/matching.py`) не сводит один товар из разных магазинов:
один привод называется по-разному (порядок слов, артикулы, описания). Пример, который
токен-нормализатор не склеит никогда, а LLM склеивает:

- mangoost: «CYMA Страйкбольный электропистолет **Beretta M92** metal slide MOSFET /зарядка через USB/**CM.126S**/»
- airgun: «Страйкбольный пистолет CYMA **CM126S** M92 зарядка через USB»

## Подход

LLM **не решает** «одинаковы ли два товара» (дорого, недетерминированно, плохо
кэшируется). Вместо этого LLM **раскладывает название на атрибуты**, а
детерминированный Python строит из них структурный ключ — обобщение уже работающего
ключа шаров (`bbs`).

```
raw_title ──► LLM (GigaChat) ──► {is_drive, brand, model, system, platform}
                                        │  (кэш по хешу названия)
                                        ▼
                     Python: канонизация → drive:brand|model|system
                                        ▼
                        детерминированный match_key (как bbs)
```

Свойства: дедуп остаётся детерминированным; кэш «замораживает» первый ответ на каждое
название (ненулевая temperature провайдера не ломает матчинг); API дёргается только
на новые названия.

## Провайдер: GigaChat (Сбер)

Выбран потому, что **из РФ Gemini/OpenAI/Claude геоблокированы**. Бесплатный тариф
`GIGACHAT_API_PERS`. У GigaChat российский корневой CA → `verify=False` (или путь к
`russian_trusted_root_ca.pem` в `GIGACHAT_CA_BUNDLE`).

`.env`:
```
GIGACHAT_AUTH_KEY=<Ключ авторизации (Basic) из кабинета GigaChat>
# опционально:
# GIGACHAT_VERIFY_SSL=true
# GIGACHAT_CA_BUNDLE=/path/to/russian_trusted_root_ca.pem
```

## Что реализовано (спайк на категории `drive`)

- `app/services/llm_extract.py` — экстракция: `GigaChatSession` (OAuth-токен с
  автообновлением + chat/completions, ретраи), строгий промпт под приводы, файловый
  кэш `.llm_cache.json`, сборка ключа `drive_key()`.
- `app/cli.py` — подкоманда `llm-extract` (недеструктивный замер + `--dry`).
- Флаг `--dry` показывает выборку **без единого вызова GigaChat**.

Запуск:
```bash
# посмотреть выборку без API:
uv run python -m app.cli llm-extract --category drive --dry --limit 80 --scan 8000
# реальная экстракция + метрика:
uv run python -m app.cli llm-extract --category drive --limit 250 --scan 8000
```

## Результаты спайка (2026-07-25)

Данные: 8000 офферов из 5 магазинов (strikeplanet, zorg, mangoost, airgun, pnevmat24).
Выборка приводов префильтром: 208 офферов.

- распознано **207/208** (1 фолбэк — не-привод корректно отвергнут);
- токен-ключ: 205 кластеров → **LLM-ключ: 189** (склеено 16 сверх токен-ключа);
- из них **4 кросс-магазинных** — все CYMA CM.12x AEP, сведённые по CM-артикулу
  между mangoost/airgun/strikeplanet под совершенно разными названиями.

Вывод: подход работает. Поле `model` после донастройки промпта берёт CM-артикул
монолитно (все 4 склейки — на нём), галлюцинаций букв нет.

Остаточная неоднозначность: **Galaxy** (у товара есть И артикул `G.xx`, И имя-реплика
типа «Walther P38») — модель колеблется между ними. Ложных склеек не даёт, но упускает
часть возможных. Правится более жёстким промптом или ручным merge в админке.

## Инфраструктура парсинга (доработано попутно 2026-07-25)

- **Логирование** (`ingest`, `cli`): старт/раздел/HTTP-запрос/heartbeat каждые 200
  офферов/итог — видно, живы ли парсеры (в stderr с таймстампами).
- **Частый коммит**: раньше коммит был только в конце прогона → обрыв терял всю
  работу. Теперь коммит каждые 200 офферов и на границе каждого раздела.
- **Возобновление** прерванного прогона: парсер отдаёт `Section(id)` после каждого
  раздела каталога; `ingest` пишет прогресс в таблицу `parse_progress` (миграция
  `b7f1a2c3d4e5`). Незавершённый прогон при следующем запуске пропускает
  обработанные разделы и продолжает с прежним `run_started_at` (чтобы деактивация
  несвежих офферов считалась корректно по всему логическому прогону). Работает для
  полных прогонов (без `--limit`).
- `parse_shops` не роняет всю пачку из-за одного упавшего магазина (per-shop
  try/except + лог).
- **Windows-dev нюанс**: async-psycopg требует `SelectorEventLoop` (починено в
  `cli._run` и `tests/conftest.py`), а Playwright-subprocess требует
  `ProactorEventLoop` — в одном процессе несовместимы. Поэтому `airsoftstore`
  (единственный Playwright-парсер) **локально на Windows не парсится**; на Linux/кроне
  (прод) конфликта нет.

## Остаётся (см. M10 в ROADMAP)

1. файловый кэш `.llm_cache.json` → таблица `title_extractions` (миграция);
2. встроить экстракцию в `matching.build_match_key` (сейчас спайк изолирован, в
   `products` не пишет); `bbs` работает параллельно;
3. схемы атрибутов для остальных категорий (`eyewear`, `uniform`, `rig`, …);
4. дожать Galaxy-кейс (артикул vs имя-реплика).

## Ключевые файлы

- `backend/app/services/llm_extract.py` — экстракция, промпт, кэш, ключ.
- `backend/app/cli.py` — команды `llm-extract` и `parse` (с логами/резюмом).
- `backend/app/services/ingest.py` — частый коммит, возобновление, `Section`.
- `backend/app/parsers/base.py` — DTO `Section`, сигнатура `iter_offers(done_sections)`.
- `backend/app/models/catalog.py` — модель `ParseProgress`.
- `backend/alembic/versions/b7f1a2c3d4e5_parse_progress.py` — миграция.
