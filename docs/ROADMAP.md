## M0 — Скелет проекта

- `backend/`: uv, `pyproject.toml` (ruff, pytest), FastAPI `app/main.py` + `GET /api/health`.
- `frontend/`: Vite + React + TS + Mantine + react-router + TanStack Query, заглушка каталога.
- `docker-compose.yml` (Postgres 16), `.env.example`, `README.md` со ссылками на docs/.

✅ **Проверка:** `uv run uvicorn app.main:app --reload` отдаёт health; `npm run dev`
показывает заглушку; `uv run pytest` зелёный (smoke-тест health); `ruff check` чистый.

## M1 — БД и auth админа

- SQLAlchemy-модели всех таблиц, Alembic init + первая миграция, seed категорий.
- `config.py` (pydantic-settings), auth админа (bcrypt + cookie), `GET /api/admin/me`.

✅ **Проверка:** `alembic upgrade head` на чистой БД; все таблицы на месте; тесты логина
(верный/неверный пароль, защищённый роут с cookie и без).

## M2 — Парсерный каркас + первый магазин

Самый рискованный этап — делается рано.

- `ShopParser` + реестр, ingest-конвейер (upsert, price_history, деактивация,
  страховочный порог), CLI `parse`.
- Парсер первого магазина (из трёх кандидатов выбрать с самой простой вёрсткой).
- HTML-фикстуры + тесты.

✅ **Проверка:** `parse --shop <code>` наполняет `offers` (выборочная сверка с сайтом
руками); повторный прогон не плодит дублей; изменение цены в фикстуре порождает строку
`price_history`; тест «0 карточек ⇒ нет массовой деактивации».

## M3 — Матчинг + остальные магазины

- `services/matching.py` (нормализация, `match_key`, авто-создание products, словари
  брендов/категорий), CLI `rematch`.
- Парсеры второго и третьего магазинов.
- Админ-API: `offers?unmatched=true`, `offers/{id}/link`.

✅ **Проверка:** после прогона трёх магазинов — выборочная ручная проверка products
с офферами из ≥2 магазинов; доля несматченных; тесты нормализатора на реальных названиях.

## M4 — Киты: модель + админка

- CRUD-API китов/позиций, `kit_pricing.py`, preview flexible-позиции.
- Фронт-админка: логин, список китов, редактор кита (fixed — автокомплит,
  flexible — критерии + предпросмотр), несматченные офферы, публикация.

✅ **Проверка:** руками собрать 2–3 реальных кита с позициями обоих типов
(одновременно приёмка UI и наполнение контентом); API-тесты CRUD и расчёта цены
(в т.ч. позиция без активных офферов).

## M5 — Публичная витрина

- `GET /api/kits` с фильтрами, деталка, `/api/meta`.
- Фронт: каталог (фильтры в URL), деталка с выбором вариантов и липким «Итого»,
  ссылки «Купить в магазине».

✅ **Проверка:** путь юзера руками: фильтр по роли+бюджету → деталка → смена варианта →
пересчёт суммы → клик уводит в магазин на верный товар; API-тесты фильтров и границ бюджета.

## M6 — Визард + поиск

- `POST /api/wizard/recommend` (скоринг: фильтр по роли/уровню + близость к бюджету).
- `GET /api/search` (pg_trgm). Фронт: Stepper и строка поиска.

✅ **Проверка:** тест скоринга (кит в бюджете выше кита сильно дороже); разные ответы
визарда → осмысленно разные рекомендации; поиск находит кит по товару из состава
и с опечаткой.

## M7 — Продакшенизация

- Деплой на VPS: docker-compose (postgres + backend + nginx со статикой фронта).
- cron на парсинг, structured-логи парсера, `pg_dump`-бэкап в cron, финальный README.

✅ **Проверка:** ночной прогон отработал по cron (лог + свежие `last_seen_at`); сайт
доступен извне; изменение цены на сайте магазина отражается после следующего прогона.

## M9 — Умный поиск по товарам (сравнение цен)

Отдельный от китов пользовательский сценарий: найти **конкретный товар** и увидеть,
где он дешевле — список магазинов с ценой, наличием и ссылкой.

- `GET /api/products/search?q=` — поиск канонического товара по названию (pg_trgm,
  терпим к опечаткам). Опционально — LLM-разбор запроса на атрибуты для точного
  попадания (та же экстракция, что и в матчинге).
- Карточка товара `/api/products/{slug}`: все офферы по магазинам с ценой, наличием
  и ссылкой «Купить»; сортировка по цене (возрастание), пометка «нет в наличии».
- **Данные уже есть**: `products` (канон) + `offers` (цена/наличие/URL по магазинам) —
  новый слой это витрина над готовой моделью. Ценность напрямую зависит от качества
  матчинга: один товар должен агрегировать офферы разных магазинов (см. M3 и
  LLM-экстракцию атрибутов) — иначе сравнивать будет нечего.
- Фронт: страница поиска `/products` и карточка `/products/:slug` (таблица «магазин —
  цена — наличие — купить»). Опционально — график истории цены (данные копятся с M2).

Приёмка: поиск находит товар по названию и с опечаткой; карточка показывает ≥2
магазина с ценами, сортировка по возрастанию, недоступные помечены.

**Готово (2026-07-25):**
- Бэкенд (`app/api/products.py`, публичный роутер `/api/products`):
  - `GET /api/products/search?q=&limit=` — pg_trgm-поиск (`word_similarity`, порог
    0.3, терпим к опечаткам). Возвращает только товары с доступным оффером
    (активный, в наличии, с ценой) — иначе сравнивать нечего; для каждого —
    минимальная цена и число магазинов. Сортировка: близость к запросу, затем цена.
  - `GET /api/products/{slug}` — карточка сравнения: все активные офферы по
    магазинам, в наличии+дешёвые сверху, недоступные ниже с пометкой; `price_min`/
    `price_max`/`shops_count` — по доступным. Схемы — `ProductSearchOut`,
    `ProductComparisonOut` в `schemas/public.py`.
  - Тесты — `tests/test_products_public.py` (8): поиск/опечатка/мин-цена/фильтр
    недоступных/min_length; карточка (сортировка по цене, out-of-stock в конец, 404).
- Фронт: `/products` (`ProductSearchPage`) и `/products/:slug`
  (`ProductComparisonPage` — таблица «магазин — цена — наличие — купить»). Ссылка
  «Сравнить цены на товары» — в шапке каталога китов.
- LLM-разбор запроса на атрибуты (опция из описания) пока не делали — базовый
  trgm-поиск закрывает сценарий; апгрейд возможен на инфраструктуре M10.
- Опциональный график истории цены (данные копятся с M2) — за рамками, как и было.

## M10 — Умный матчинг через LLM (экстракция атрибутов)

Проблема: токен-`match_key` не сводит один товар из разных магазинов (разные
формулировки, порядок слов, артикулы). Решение — LLM раскладывает название на
атрибуты (бренд/модель/тип), из которых детерминированный Python строит структурный
ключ (обобщение ключа шаров `bbs`). Провайдер — **GigaChat** (доступен из РФ;
Gemini/OpenAI/Claude геоблокированы). Полный дизайн, как запускать и что сделано —
в [LLM_MATCHING.md](LLM_MATCHING.md).

**Спайк готов (2026-07-25):** категория `drive`, GigaChat, файловый кэш экстракции.
На 208 приводах из 5 магазинов: 207/208 распознаны, LLM-ключ склеил 16 кластеров
сверх токен-ключа, из них **4 кросс-магазинных** (CYMA CM.12x AEP под разными
названиями в разных магазинах — токен-нормализатор их не сводит). Недеструктивно
(в `products` не пишет). Запуск: `uv run python -m app.cli llm-extract --category
drive [--dry] --limit N`.

**Остаётся (продакшенизация):**
1. файловый кэш `.llm_cache.json` → таблица `title_extractions` (миграция);
2. встроить экстракцию в `matching.build_match_key` (сейчас спайк изолирован);
   `bbs` продолжает работать параллельно;
3. схемы атрибутов для остальных категорий (`eyewear`, `uniform`, `rig`, …) — тот
   же механизм, свой шаблон ключа на категорию;
4. дожать неоднозначные кейсы (Galaxy: артикул `G.xx` vs имя-реплика — модель
   колеблется; не даёт ложных склеек, но упускает часть возможных).

Приёмка: после интеграции доля кросс-магазинных товаров (product с офферами из ≥2
магазинов) растёт против чистого токен-ключа; ручной merge в админке — safety net.
Связано с M9 (умный поиск «где дешевле» опирается на качество этого матчинга).

## Осознанно за рамками MVP

Корзина/заказы (схема готова: добавятся `users`, `carts`, `cart_items → offer_id`),
регистрация, UI-мерж дублей products, графики истории цен (данные копятся с M2),
алерты на падение цены, полноценный FTS-ранкинг, картинки через свой прокси/CDN,
запуск парсинга кнопкой из админки.
